:::section kicker="Requirements" headline="What a public deployment needs"
The app runs and you can play it. To let anyone else play it, several conditions have
to be met.

:::figure id="four-problems" caption="Every service in this course addresses one of these operational needs."
:::

1. **The program runs somewhere that stays on.** Cloud Shell shuts down when
   you stop using it.
2. **That location has a public address**, rather than one that means *this
   computer*.
3. **Someone operates the building**: power, cooling, networking, and replacing
   failed hardware.
4. **Someone pays for it.**

:::key
When a service is unfamiliar later in this course, ask which of these requirements it
addresses.
:::
:::

:::section kicker="Addressing" headline="How localhost routing works"
The app is listening on `localhost:8080`. `localhost` means *this computer*: a
request to it never leaves the machine that made it.

:::figure id="localhost" caption="A request to localhost never leaves the computer that made it."
:::

Cloud Shell's Web Preview gives that port a URL you can open, but it is a
private connection to your session. Sending it to someone else gets them a
sign-in page, not your game.
:::

:::section kicker="Workbench" headline="How the exercises work"
Most exercises don't give you a command to copy. They ask you to describe what
you need in your own words, the way you would ask an assistant. If the request
is correct, the workbench runs the matching command in your Cloud Shell and
shows you what it ran.

:::note
If a request is not accepted, the response explains what is missing. Nothing
blocks you, and you can try again as many times as you want.
:::
:::

:::section kicker="Architecture" headline="Target cloud architecture"
By the end of the course, DinoQuest has a public address, a leaderboard that
survives a restart and is shared by everyone playing, permissions that control
what it can reach, and a dinosaur generated by a model. You will also know what
each of those costs.
:::
